# 입력 목표값 충전 제한과 바이패스 유지

CLI `v1.3.5-local-firmware.1`, GUI `1.4.1-local.1`.

`battery maintain N`의 입력값 N을 충전 상한으로 사용한다. 목표 도달 후 어댑터 공급을 유지하고, 배터리 충·방전이 거의 없는 상태를 센서로 확인한다. 코드 구현과 격리된 모의 시험을 완료했다. 단일 기기의 28시간 32분 운용 로그 중 10시간 23분 구간에서 바이패스 판정과 표시 잔량 61% 유지를 확인했다. 설정 목표는 60%다. 목표 아래에서 충전해 도달하는 동작, 하한 재충전, 잠자기와 재부팅은 미검증이다.

이 문서에서 소스 경로는 저장소 루트 기준이며, `.battery`로 시작하는 실행 데이터 경로는 사용자 홈 기준이다.

## 입력 정책

| 명령 | 동작 |
| --- | --- |
| `battery maintain N` | 정수 1~99. 상한 N, 재충전 하한 max(0,N-2)를 적용한다. |
| `battery maintain 060` | 십진수 60으로 정규화한다. `08`도 십진수 8이다. |
| `battery maintain N --force-discharge` | 목표보다 높은 잔량에서만 초기 방전을 수행한다. N에 도달하면 어댑터 입력을 복구한다. |
| `battery maintain 100` | 범위 제한을 해제하고 완전 충전을 허용한다. 별도의 바이패스 보장 모드는 아니다. |
| `battery maintain stop` | 제한을 해제하고 활성 상태를 끈다. 마지막 목표와 초기 방전 선택은 보존한다. |
| `battery maintain recover` | 활성 상태였던 정책만 복구한다. 명시적으로 중지했다면 다시 켜지 않는다. |

N은 최대 충전량이며, 매 순간 표시 잔량을 정확히 N으로 고정하는 값은 아니다. N-2는 재충전 여유폭이다. 목표 도달 후 N-2까지 일부러 방전시키지 않는다. 60/58과 96/94는 같은 계산 경로의 사례다. 매우 낮은 목표 등 개별 값의 실기 지원은 쓰기 검증과 실제 동작을 구분해 평가한다.

빈 입력·0·음수·소수·100 초과·문자·알 수 없는 옵션은 기존 정책을 변경하지 않고 거부한다. 새 펌웨어 경로에서는 범위 입력·전압 유지·수동 충전/어댑터 조작·보정을 아직 연결하지 않았다. 해당 명령은 현재 제한을 해제하기 전에 거부한다. 다른 기기용 기존 충전 경로는 남겨 두었다.

## 제어와 복구

`firmware.sh`가 입력 검증, 펌웨어 적용, 제어자 인계, 전력 상태 판정을 담당한다. `battery.sh`는 기존 유지 경로보다 먼저 새 경로로 요청을 전달한다. GUI는 `status_json`을 읽고 CLI에 요청하며 별도 충전 루프를 실행하지 않는다.

적용은 입력 검증 → 단일 제어권 확보 → 이전 제어자 일시 정지 → 이전 상태 기록 → 새 값 쓰기와 읽기 확인 → 정책 저장 → 새 유지 작업 준비 확인 순서로 진행한다. 실패하면 이전 정책·제어값·프로세스 상태로 복구한다. 복구 실패는 별도 로그로 남긴다. 사용자 설정 파일을 실행 가능한 코드로 읽지 않는다.

| 항목 | 구현 |
| --- | --- |
| 제어키 | `bfF0` 활성값 02, `bfD0` 상한, `bfE0` 하한 |
| 적용 순서 | 비활성화 → 상한 → 하한 → 활성화. 퍼센트는 4바이트 리틀 엔디언 |
| 성공 판단 | 종료 코드뿐 아니라 오류 출력과 원시 바이트 읽기 결과까지 확인 |
| 반복 요청 | 같은 목표·옵션·적용값·실행 상태라면 제한을 끄고 켜지 않음 |
| 유지 주기 | 약 60초. 정상 상태에서는 읽기로 확인 |
| 정책 유실 | 비활성/초기화된 경우 요청당 한 번 복구 시도. 다른 활성 정책과 충돌하면 덮어쓰기를 반복하지 않음 |
| 초기 강제 방전 | 같은 유지 작업이 처리. 별도의 기존 방전 루프를 병행하지 않음 |
| 일반 종료 | 유지 작업만 끝나도 펌웨어 상한은 남음. 작업이 소유한 어댑터 차단은 종료 시 복구 |
| 명시적 중지 | 상한 해제·어댑터 복구·활성 상태 중지. GUI 시작이나 로그인 복구로 재개하지 않음 |

다른 프로그램이 적용한 것으로 보이는 활성 범위를 처음부터 임의로 인수하지 않는다. 적용된 설정과 실제 전원 사용은 구분한다. 명령 성공은 키 적용과 유지 작업 준비를 뜻하며, 목표 도달과 바이패스 실측 완료를 뜻하지 않는다.

새 SMC 권한은 `battery.sh`의 `visudoconfig`에 추가된다. `bfD0/bfE0`의 0~100 인코딩과 `bfF0`의 00/02만 열거한다. 임의 키·임의 명령 실행 권한을 추가하지 않는다. 실행 모듈과 설치 디렉터리는 root 소유이며 일반 사용자가 쓰지 못해야 한다.

## 상태와 바이패스 확인

`battery status`와 `battery status_json`은 요청 목표, 적용 상태, 전원 사용 상태를 구분해 출력한다. GUI도 같은 응답을 사용한다. 기존 `status_csv`는 읽기 호환용으로 유지한다.

| 상태 | 의미 |
| --- | --- |
| `applied=verified` | 요청한 제어값과 유지 작업이 확인됨 |
| `power=charging` | 신선한 측정에서 충전 중 |
| `power=initial_discharge` | 사용자가 선택한 초기 방전 단계 |
| `power=external_unconfirmed` | 외부 전원은 연결됐으나 배터리 사용 상태가 바이패스 조건을 충족하지 않음 |
| `power=external_verifying` | 외부 전원 유지 관측 중. 아직 5분 조건 미충족 |
| `power=bypass_verified` | 아래 관측 조건 충족 |
| `power=unknown` | 측정·적용·실행 상태를 확정할 수 없음 |
| `power=limit_failed` | 목표 도달 후 충전 전류와 용량 증가가 연속 관측됨 |

바이패스는 어댑터가 맥에 전력을 공급하고 배터리 충·방전이 거의 없는 상태다. 배터리가 회로에서 물리적으로 분리됐다는 의미는 아니다. 목표 도달 후 최소 5분의 연속 관측에서 다음을 만족해야 한다.

- 서로 다른 센서 갱신이 4회 이상이며, 측정 나이는 120초 이내다.
- 외부 전원 연결, 충전 중 아님, 배터리 전류 ±100mA 이내다.
- 원시 용량 변화 폭이 `max(5mAh, 원시 최대 용량의 0.1%)` 이하다. 정수 연산에서는 0.1%를 내림하므로 약간 더 엄격하다.
- 외부 입력이 1W를 넘고, 배터리 전력 및 외부 입력과 시스템 부하의 차이는 각각 2W 이내다.
- 잔량은 목표 부근 N±1%p다. 이 범위는 측정 여유이며, 상한 초과 충전을 허용하는 설정이 아니다.

센서 정체·연결 변경·충전 재개·용량 변화가 있으면 관측창을 초기화한다. 상태 조회도 오래된 바이패스 결과를 그대로 표시하지 않으며, 현재 연결과 전류를 다시 읽는다. 목표 도달 후 서로 다른 갱신에서 양의 전류와 원시 용량 증가가 두 번 연속 관측되면 실패로 기록한다.

허용치는 초기 검증 기준이다. 별도의 수동 시험에서는 목표 도달 후 5분 이상 전류 0mA, 원시 용량 일정, 외부 전원 공급을 관측했다. 이는 새 코드 전체의 실기 인수 시험을 대체하지 않는다.

## 로그와 실행 파일

다음 경로는 사용자 홈을 기준으로 한다.

| 상대경로 | 용도 |
| --- | --- |
| `.battery/battery.log` | CLI와 펌웨어 적용·관측·실패·복구 로그 |
| `.battery/gui.log` | GUI의 요청·표시·오류 로그 |
| `.battery/maintain.percentage` | 마지막으로 적용에 성공한 목표값 |
| `.battery/firmware.policy` | 활성 상태, 목표, 초기 방전 선택, 요청 식별값 |
| `.battery/firmware.status` | 최근 관측 결과. 로그를 대체하는 이력 파일은 아님 |
| `.battery/battery.pid` | 유지 작업 PID. 이것만으로 실제 적용을 판단하지 않음 |

로그는 `battery logs 100`으로 확인한다. 상태 변경 시 즉시, 상태가 같으면 약 10분마다 요약을 남긴다. 요약에는 목표, 적용/전원 상태, 잔량, 전류, 원시 용량, 외부 입력, 시스템 부하와 센서 갱신 시간이 포함된다. 전체 로그가 5MB를 넘으면 CLI 실행 시 최근 2,000줄을 남긴다. 테스트 자료가 필요하면 그 전에 보관한다.

대표 이벤트는 `event=apply`, `event=initial_discharge`, `event=initial_phase_complete`, `event=observation`, `event=write_failed`, `event=rollback`, `event=policy_recovered`다. `power=bypass_verified`는 실제 관측 조건 통과 후에만 기록된다. 기존 설치본도 같은 CLI 로그 파일을 사용하지만 새 이벤트는 로컬 버전을 설치·실행한 뒤부터 생긴다.

## 설치와 사용자 실기 확인

저장소 루트에서 실행한다.

```sh
./install-local.sh
battery maintain 60
battery status
battery logs 100
```

60은 예시다. 원하는 정수로 바꾼다. 설치는 로컬 파일과 SMC 권한을 설치하며 정책을 자동 시작하지 않는다. 관리자 인증은 설치 때 필요하다. 기존 GUI를 종료한 뒤 새 CLI를 적용한다. GUI 소스도 함께 수정했으므로 기존 설치된 GUI와 새 소스의 동작을 혼동하지 않는다. 새 GUI는 `app`에서 의존성을 설치한 뒤 실행하거나 빌드한다.

`setup.sh`는 로컬 설치 진입점으로 바꿨다. 이 로컬 빌드의 CLI·GUI 자동 업데이트는 공식 버전으로 덮어쓰지 않는다. 이후 갱신도 로컬 체크아웃을 검토한 뒤 `install-local.sh`로 한다.

사용자 확인은 배터리 잔량이 목표보다 낮아진 뒤 실제로 충전되는지, 목표에서 멈추는지, 이후 `power=bypass_verified`가 기록되는지 순서로 진행한다. 키 적용만 확인한 `event=apply`와 구분한다. 실패·확인 불가가 나오면 해당 시각 전후의 `battery logs 200` 결과를 보관한다. 목표 부근 유지와 24시간을 넘는 운용 기록은 아래에서 정리했다. 정확한 60% 도달·하한 재충전·잠자기·재부팅 및 24시간 연속 바이패스 판정은 남은 인수 항목이다.

## 자동 검증

저장소 루트에서 다음을 실행한다. 테스트는 임시 디렉터리의 가짜 SMC와 제어자만 사용하며 시스템 충전 설정을 쓰지 않는다.

```sh
python3 -m unittest discover -s tests -p 'test_*.py' -v
node --test tests/test_status.js tests/test_gui.js
bash -n battery.sh
bash -n firmware.sh
```

입력 정규화, 동적 상·하한, 종료 코드 0인 SMC 오류, 부분 실패 복구, 작업 시작 실패 복구, 동시 요청, 초기 방전 후 복귀, 중지·복구, 센서 정체, GUI의 목표 보존과 시간 초과 처리를 검증한다. GUI 패키징·서명 및 실제 배터리 전원 전환은 이 자동 시험의 범위가 아니다.

## 실기 검증 결과

단일 Apple Silicon Mac의 macOS Sequoia 15.8.1 환경에서 로컬 빌드의 `battery maintain 60`을 적용했다. 상한 60%, 하한 58%, 초기 강제 방전 옵션 미사용 상태다. 초기 `event=apply result=verified` 이후의 고정된 로그 구간을 분석했으며, 기록 시각과 프로세스·기기 식별자는 공개하지 않는다.

| 항목 | 관측 결과 |
| --- | --- |
| 설정 적용부터 마지막 관측까지 | 28시간 32분 33초, 관측 요약 172건 |
| 최초 바이패스 판정부터 마지막 관측까지 | 10시간 23분 6초, `bypass_verified` 요약 63건 |
| 바이패스 구간 표시 잔량 | 61% |
| 해당 구간 배터리 전류와 전력 | 63건 모두 0mA, 0mW |
| 해당 구간 원시 용량 | 3,594~3,598mAh, 변동 폭 4mAh |
| 해당 구간 외부 입력과 시스템 부하 | 12,090~21,529mW, 각 기록에서 두 값이 일치 |
| 최초 판정 이후 다른 전원 상태 기록 | 없음 |
| 분석 구간의 제한 실패·쓰기 실패·복구 이벤트 | 없음 |
| 관측 요약 사이 최대 간격 | 605초 |

이 운용은 목표보다 높은 95%에서 시작해 63~62%를 거쳐 61%로 내려온 경로다. 목표 아래에서 충전해 60%에서 멈추는 경로를 검증한 것은 아니다. 앞선 구간에도 전류가 0인 기록은 있었지만 표시 잔량 등 판정 조건이 충족되지 않아 `external_unconfirmed`로 남았다. 설정값 60%와 표시값 61%의 차이 원인은 추가 검토가 필요하며, 정확히 60% 고정을 확인했다고 주장하지 않는다.

10시간 23분은 최초·마지막 바이패스 요약 사이의 경과 시간이다. 상태 변경 시와 약 10분마다 저장된 요약 기록에서 판정이 이어졌다는 의미이며, 매 순간을 독립 계측한 결과나 24시간 연속 바이패스 증거로 확대하지 않는다. `bypass_verified`는 앞서 정의한 소프트웨어 관측 기준의 통과를 뜻하며, 회로의 물리적 분리를 증명하지 않는다.

## 남은 검증과 공식 배포 통합

- 목표 아래에서 충전을 시작해 멈추는 지점과 60% 설정 대비 61% 표시 차이.
- 58% 하한에서 재충전 시작 및 목표 부근 재진입.
- 잠자기·깨우기, 재부팅, 충전기 분리·재연결 후 정책과 관측 복구.
- 24시간 연속 바이패스 판정 및 더 긴 기간의 전원·용량 안정성.
- 다른 Mac 모델·펌웨어·목표값에서의 실기 동작과 기존 제어 경로의 호환성.
- 새 GUI 패키징·서명과 실제 GUI 조작. 자동 시험은 GUI 로직을 모의 검증한 것이다.

현재 변경은 로컬 빌드용이다. `setup.sh`는 체크아웃이 있어야 동작하며 `update.sh`와 CLI·GUI 자동 업데이트는 공식 버전으로 덮어쓰지 않도록 변경돼 있다. 공식 한 줄 설치, GUI 최초 설치, 릴리스 업데이트 흐름에 통합할 방식이 정해지기 전까지 Draft PR로 검토한다.

공개 변경에는 개인 경로, 계정명, 호스트명, 기기 식별자, 원본 진단 로그와 Finder 메타데이터를 포함하지 않는다. 소스 경로는 저장소 기준, 실행 데이터 경로는 사용자 홈 기준으로 표시한다. 설치 코드에서 사용하는 고정 시스템 경로는 보안 및 실행 동작을 위해 유지한다.
